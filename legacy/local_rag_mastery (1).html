Local Context Lab — RAG Mastery

Roll-your-own local RAG  //  Architecture · Code · Closed loop

// The one idea everything hangs off

"The LLM is not the system. The system is the loop around the LLM."

A RAG product is not "chat with your docs." It is a closed loop: Data → Retrieval → Generation → Logging → Feedback → Evaluation → Improvement. The model is one swappable component. The durable engineering — the part that makes an AI product safe, auditable, and improvable — is the deterministic machinery wrapped around it: how you chunk, what you retrieve, how you constrain generation, what you log, and how you measure whether a change made things better or worse. Master that loop here and you can build it for any company.

LAYER 01 // RETRIEVAL

Find the right evidence

Ingest, chunk, embed, store, and fetch the top-k chunks for a query. If the right chunk isn't here, no model can save you. Debug retrieval before you ever touch the prompt.

LAYER 02 // GENERATION

Answer only from evidence

A constrained prompt forces the model to answer from retrieved context, cite sources, and refuse when context is missing. Grounded before smart.

LAYER 03 // THE LOOP

Observe, label, improve

Every run leaves a trace in SQLite. Feedback classifies failures. Evals tell you if a change helped. This is what turns a demo into a product.

The five design principles — say them out loud, they justify every choice

Local-first

All core data and inference stay on the machine (Ollama + Chroma + SQLite). No cloud dependency. This is the foundation of the "closed-loop, safer stack" story — nothing leaves the boundary you control.

Grounded before smart

Prioritize source-grounded retrieval and citations over fluent prose. A confidently wrong answer is worse than "the context is insufficient."

Retrieval before generation

Build and debug the retrieval-only CLI first. Confirm the right chunks come back before you ask the LLM to write anything. Most "bad answers" are bad retrieval.

Human-in-the-loop

The system suggests; the human decides. Feedback drives improvement. No autonomous mutation of source material in the MVP.

Observable by default

Every answer leaves a trace: query, retrieved chunks, answer, model, sources cited, feedback, failure notes. You cannot improve a system you cannot see.

The maturity ladder — never skip a rung

The single biggest mistake in AI products is adding autonomy before observability. The correct path is bottom-up:

Grounded answers→ Citations→ Logs→ Feedback→ Evals→ Recommendations→ Human-approved actions→ Limited automation

When you advise a company on a "safer AI stack," this ladder is the spine of the advice: prove the system is grounded and observable before you give it any power to act.

The one decision worth understanding deeply: rebuild vs. upsert

                

                    

                        
Your choice: delete_collection then add (rebuild)

                        
Every run wipes the collection and re-indexes from scratch. Pro: dead simple, and the index always exactly matches what's on disk — no stale or orphaned chunks, ever. Perfect for an MVP where you re-ingest the whole small corpus each time.

                    

                    

                        
The alternative: upsert with deterministic IDs

                        
Re-embed only what changed; same id overwrites. Pro: fast incremental updates on a large corpus. Con: if a doc shrinks, old chunk IDs linger as orphans unless you reconcile. More moving parts.

                    

                

                
For a single-user local lab, your rebuild approach is the right call — simpler and self-correcting. Reach for upsert only when re-embedding everything starts to feel slow. Knowing when to switch is the expert move, and you've already picked correctly for where you are.

                The thesis
                
"The LLM is not the system. The system is the loop around the LLM."

                
Data → Retrieval → Generation → Logging → Feedback → Evaluation → Improvement. The model is swappable; the loop is the product.

            


            

                

                    Query path
                    
query → embed query → Chroma top-k chunks → build constrained prompt (label each source, "answer only from context, cite, refuse if missing") → llama3.1:8b → answer + citations → SQLite run log → feedback.

                

                

                    Ingestion path
                    
read data/raw/*.md → extract metadata → chunk (~800 chars / 120 overlap, keep heading) → embed via nomic-embed-text → upsert to Chroma with deterministic IDs (re-run never duplicates).

                

            


            

                Two storage layers — different jobs
                
Chroma answers "which chunks are semantically relevant?" (vectors + metadata). SQLite answers "what happened, was it useful, how do we improve?" (rag_runs, rag_run_sources, feedback, eval_results). Chroma stores what the retriever needs; SQLite stores what the product needs.

            


            

                Failure taxonomy — classify before you fix
                

                    
bad_retrieval
Right source not in top-k. Fix: chunking, metadata, top-k, hybrid search, reranking.

                    
missing_source
Data isn't in the KB at all. Fix: add the doc, improve ingestion coverage.

                    
unsupported_answer
Right chunks retrieved, model claimed beyond them. Fix: stronger prompt, less noise, citation-per-claim.

                    
bad_citation
Cited a source that doesn't support the claim. Fix: prompt, citation validation.

                    
unclear_question
Query too broad/ambiguous. Fix: clarify, query rewriting, mode selection.

                    
false-green eval
Passed on keywords but answer is wrong. Fix: better grounding checks, LLM-as-judge later.
